2. Résumé / Abstract

Résumé

Agria est une application mobile et web destinée aux agriculteurs en coopérative. Elle propose une carte satellite interactive permettant de tracer et gérer des parcelles agricoles, un module de diagnostic de maladies des cultures en trois étapes, un suivi météorologique en temps réel avec prévisions sur cinq jours, et des prédictions agronomiques (estimation de récolte, besoins en eau, fertilisation).

Le projet repose sur une architecture double : une version web historique en HTML/CSS/JavaScript vanilla, et une version mobile développée avec le framework Expo React Native (SDK 54, TypeScript, expo-router). Les données sont synchronisées via Firebase Realtime Database avec un fallback en stockage local (AsyncStorage / localStorage). Le design suit le thème « Golden Hour » inspiré des champs de blé au coucher de soleil.

Abstract

Agria is a mobile and web application designed for cooperative farmers. It features an interactive satellite map for parcel management, a three-step crop disease diagnostic tool, real-time weather monitoring with five-day forecasts, and agronomic predictions. Built with Expo React Native and Firebase Realtime Database, it offers offline-capable data persistence and a warm “Golden Hour” design system.

3. Introduction

3.1 Contexte

L’agriculture française fait face à des défis majeurs : changement climatique, pression sur les rendements, nécessité de réduire les intrants, et vieillissement de la population agricole. Dans ce contexte, la digitalisation des exploitations n’est plus un luxe mais une nécessité. Pourtant, les solutions existantes restent souvent coûteuses, complexes, ou mal adaptées aux petites et moyennes exploitations.

Les coopératives agricoles, qui regroupent des centaines d’exploitants, ont besoin d’outils simples et accessibles pour aider leurs membres à mieux gérer leurs parcelles, identifier rapidement les maladies, et anticiper les conditions météorologiques.

3.2 Problématique

Comment fournir aux agriculteurs d’une coopérative un outil mobile, intuitif et gratuit leur permettant de :

  • Cartographier et gérer leurs parcelles sur fond satellite
  • Diagnostiquer les maladies de leurs cultures en quelques clics
  • Consulter la météo et les prévisions localisées
  • Stocker leurs données de manière sécurisée et accessible partout

3.3 Objectifs

  • Développer une application mobile iOS/Android avec React Native
  • Maintenir une version web de référence en vanilla JavaScript
  • Intégrer une carte satellite interactive avec outils de dessin
  • Proposer un diagnostic de cultures en trois étapes (culture, symptômes, localisation)
  • Assurer la synchronisation cloud des données avec persistance locale
  • Appliquer un design system cohérent et chaleureux adapté au monde agricole

Le marché des outils numériques agricoles est en pleine expansion. Plusieurs solutions commerciales existent, mais présentent des limitations pour notre public cible :

Le choix de React Native via Expo a été motivé par la productivité (hot reload, expo-router pour le routing fichier), l’accès aux APIs natives (haptiques, notifications, safe areas) sans configuration complexe, et la réutilisation des compétences JavaScript existantes du projet web.

4.3 Cartographie — Leaflet et OpenStreetMap

Le choix de Leaflet.js couplé aux tuiles satellite ArcGIS/Esri s’est imposé face à Google Maps (payant au-delà d’un quota) et Mapbox (coût élevé). Leaflet est léger (~40 Ko), open-source, et offre des fonctionnalités avancées comme le dessin de polygones, le snapping (aimantation), et le géocodage via Nominatim (OpenStreetMap).

Sur mobile, Leaflet est intégré dans une WebView (react-native-webview), ce qui permet de réutiliser le même code cartographique entre les deux plateformes tout en bénéficiant du rendu natif pour le reste de l’interface.

4.4 Backend — Firebase vs Supabase

Le projet a démarré avec Supabase (PostgreSQL), mais a migré vers Firebase Realtime Database pour plusieurs raisons : gratuité plus généreuse au niveau starter, synchronisation temps réel native, SDK JavaScript compatible React Native sans configuration supplémentaire, et simplicité du modèle clé-valeur (pas de schéma SQL à maintenir).

Un système de persistence hybride a été conçu : chaque écriture est stockée dans AsyncStorage (mobile) / localStorage (web) et dans Firebase. À la lecture, le stockage local est interrogé en priorité (réponse instantanée), puis Firebase est vérifié en arrière-plan.

5. Analyse des besoins

5.1 Besoin identifié

Lors de nos échanges avec des membres de coopératives agricoles, plusieurs constats ont émergé :

  • Manque d’outils simples : les logiciels existants (Geofolia, MesParcelles) sont perçus comme complexes et chronophages.
  • Besoin de mobilité : les agriculteurs sont sur le terrain, pas devant un bureau. Le téléphone est l’outil le plus accessible.
  • Diagnostic rapide : identifier une maladie tôt peut sauver une récolte. Un outil d’aide au diagnostic, même simple, a une vraie valeur.
  • Partage encadré : dans une coopérative, voir les parcelles des autres est utile, mais les données personnelles doivent rester protégées.
  • Prévisions fiables : la météo est le facteur n°1 de décision au quotidien.

5.2 Personas utilisateurs

5.3 Cas d’usage

  1. Cartographie des parcelles — L’agriculteur trace sa parcelle sur la carte satellite, lui attribue un nom, une culture, une date de semis.
  2. Consultation météo — Depuis le tableau de bord, il vérifie la température, l’humidité et les prévisions à 5 jours pour sa commune.
  3. Diagnostic d’une maladie — En trois étapes (choix de la culture, sélection des symptômes, localisation), l’application identifie la maladie probable et propose des recommandations.
  4. Prédictions agronomiques — Estimation de récolte, besoins en eau et fertilisation calculés selon la culture et les conditions locales.
  5. Administration — L’administrateur accède à un back-office pour gérer les utilisateurs, consulter les parcelles et les logs.

6.2 Design system Golden Hour

Le design system « Golden Hour » s’inspire de la lumière chaude des champs de blé au coucher de soleil. Il repose sur trois piliers :

  • Palette crème/chaud : fond #FDF8EE, accent blé #E8B84B, texte brun #3D2E1F
  • Typographie duale : Fraunces (serif chaud) pour les titres, Outfit (géométrique) pour le corps et l’UI
  • Ombres chaudes : box-shadow avec une teinte brune plutôt que noire, pour une profondeur naturelle
  • Animations fluides : basées sur react-native-reanimated, easing curves naturelles, transitions de 200-300ms

Ce thème est verrouillé en mode clair uniquement (color-scheme: light), choix assumé pour renforcer l’identité visuelle chaleureuse et la lisibilité en extérieur.

6.3 Parcours utilisateur

  1. Connexion — Écran de login obligatoire à la première ouverture (sauf admin).
  2. Dashboard — Vue d’ensemble : météo actuelle, prévisions, alertes, liste des parcelles.
  3. Carte — Carte satellite Leaflet en WebView avec outils de dessin, badges de parcelles, recherche de commune.
  4. Diagnostic — Workflow 3 étapes : sélection culture → symptômes → localisation → résultat avec recommandations.
  5. Profil — Informations utilisateur, préférences, historique des diagnostics.
  6. Admin (back-office) — Gestion des utilisateurs, consultation des parcelles, logs système.

8. Problèmes rencontrés et solutions

Cette section détaille les principaux obstacles techniques et fonctionnels rencontrés au cours du développement, ainsi que les solutions mises en œuvre pour les résoudre.

8.1 Migration Supabase → Firebase

Problème : Le projet initial utilisait Supabase (PostgreSQL) comme backend. La configuration des tables, des politiques RLS (Row Level Security), et la gestion des tokens JWT se sont avérées trop complexes pour un projet de cette taille. De plus, le SDK Supabase pour React Native présentait des problèmes d’initialisation.

Solution : Migration complète vers Firebase Realtime Database. Le modèle clé-valeur (JSON tree) élimine le besoin de schéma SQL et de migrations. Le SDK Firebase est natif React Native. La base « projet-etude-2026 » hébergée en Europe (europe-west1) garantit la conformité RGPD.

8.2 Carte Leaflet dans une WebView React Native

Problème : Leaflet.js est une bibliothèque DOM. L’intégrer directement dans React Native est impossible sans WebView. La communication entre le code React Native (TypeScript) et le code Leaflet (JavaScript dans la WebView) nécessite un pont de messages.

Solution : Utilisation de react-native-webview avec un système de messages postMessage / onMessage. Le HTML Leaflet est injecté dans la WebView, et les événements (clic sur parcelle, fin de dessin, etc.) sont relayés au code React Native pour mise à jour de l’état et persistance.

8.3 Dessin de polygones sur mobile

Problème : La fonction de dessin de parcelles était difficile à utiliser sur mobile : le point de départ était trop petit pour être cliqué avec le doigt, la fermeture manuelle du polygone échouait souvent.

Solution :

  • Élargissement de la zone de clic du premier point (hitbox augmentée)
  • Fermeture automatique du polygone lorsque l’utilisateur approche du point d’origine
  • Système de snapping (aimantation) aux parcelles adjacentes pour éviter les chevauchements

8.4 Safe areas et bordures iPhone

Problème : Sur iPhone (notch, Dynamic Island), certains éléments de l’interface passaient sous la caméra frontale. En bas, les éléments disparaissaient derrière la barre de contrôle (Home Indicator).

Solution : Intégration de react-native-safe-area-context et application de padding top/bottom calculés dynamiquement via useSafeAreaInsets(). Application du hook sur tous les écrans (layout racine, bottom sheet de la carte, panneau de configuration).

8.5 Badges de parcelles instables

Problème : Les badges affichant le nom des parcelles sur la carte ne suivaient pas correctement leur parcelle lors du zoom/dézoom. Ils étaient parfois décalés ou disparaissaient.

Solution : Ancrage des badges au barycentre (centre de masse) de chaque polygone plutôt qu’au premier point. Recalcul de la position à chaque événement de zoom (zoomend) et de déplacement (moveend). Visibilité masquée automatiquement lorsque le badge sort de la zone visible de la carte.

8.6 Authentification et flux de connexion

Problème : La page de login ne s’affichait pas systématiquement à l’ouverture de l’application mobile. Certains utilisateurs accédaient directement au dashboard sans être identifiés, causant des incohérences de données.

Solution : Mise en place d’un guard d’authentification dans le layout racine (_layout.tsx) qui vérifie la présence d’un identifiant utilisateur valide. Si absent, redirection forcée vers /login. Exception pour l’accès admin qui utilise son propre mécanisme de vérification. Le login force également la création d’une entrée utilisateur dans Firebase pour garantir la persistance.

8.7 Synchronisation localStorage ↔ cloud

Problème : Sans connexion internet, l’application devait continuer à fonctionner. Mais à la reconnexion, les données locales pouvaient entrer en conflit avec les données distantes.

Solution : Stratégie local-first avec écriture traversante : chaque sauvegarde écrit d’abord en local, puis tente l’écriture cloud. Si le cloud est indisponible, l’écriture locale est conservée sans erreur. À la prochaine connexion réussie, la donnée est poussée. Pas de résolution de conflits complexes : la dernière écriture gagne (last-write-wins).

8.8 Clavier et scroll dans les formulaires

Problème : Dans le panneau de configuration des parcelles, le clavier masquait les champs de saisie (notes, date de semis). Le scroll ne remontait pas automatiquement.

Solution : Implémentation d’un KeyboardAvoidingView avec comportement padding. Ajout d’un DateWheelPicker personnalisé pour éviter le clavier natif sur la date de semis. Bouton de fermeture explicite du clavier sur le champ notes.

9. Conclusion & perspectives

9.1 Bilan

Le projet Agria a abouti à une application fonctionnelle couvrant l’ensemble des cas d’usage identifiés :

  • Version mobile React Native avec 7 écrans, bottom tab navigation, back-office admin
  • Version web vanilla de référence avec 5 pages
  • Carte satellite interactive avec dessin et badges de parcelles
  • Diagnostic de 15 maladies sur 5 cultures avec recommandations
  • Météo temps réel et prévisions 5 jours
  • Persistance hybride locale + cloud (Firebase)
  • Design system cohérent Golden Hour sur les deux plateformes

Le projet a suivi 62 commits d’évolution, partant d’un simple prototype web pour aboutir à une application mobile complète avec authentification, synchronisation cloud, et administration.

9.2 Acquis techniques

  • Maîtrise d’Expo React Native et expo-router
  • Intégration de Leaflet.js dans une WebView React Native
  • Conception d’un système de persistance local-first avec Firebase RTDB
  • Mise en place d’un design system complet (palette, typographie, composants, animations)
  • Gestion des spécificités mobiles : safe areas, haptiques, notifications push, gestes

9.3 Perspectives

Plusieurs axes d’amélioration sont envisagés pour les versions futures :

  • Analyse de sol : intégration de données pédologiques (type de sol, pH, matière organique) via API géospatiales (INRAE, GISSol) pour enrichir les recommandations.
  • Recommandations IA : remplacer le moteur de matching pondéré par un modèle de classification plus avancé, voire un LLM spécialisé en agronomie.
  • Mode hors-ligne complet : mise en cache des tuiles cartographiques pour un usage sans connexion dans les zones blanches.
  • PWA : transformation de la version web en Progressive Web App pour une expérience unifiée.
  • Intégration Agrichat : conseils contextualisés sur les intrants et solutions de traitement.
  • Couverture de cultures élargie : ajout de l’orge, du pois, de la betterave, et des cultures maraîchères.
  • Cartographie avancée : calcul automatique de surface (hectares) à partir du polygone dessiné.
Agria démontre qu’il est possible de concevoir un outil agricole moderne, mobile, gratuit et accessible, en s’appuyant exclusivement sur des technologies open-source et des APIs publiques. Le projet pose les fondations d’une plateforme plus ambitieuse au service des coopératives.
